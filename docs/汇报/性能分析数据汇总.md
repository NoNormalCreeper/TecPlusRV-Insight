# 答辩性能分析数据汇总

本文档汇总当前仓库中适合用于答辩的数据，重点服务以下要求：

- 分析系统性能瓶颈并提出优化方案；
- 引入流水线机制，并与多周期核心进行量化对照；
- 对时钟频率、CPI 与吞吐量进行量化评估；
- 展示 custom-0 DOT4 指令的性能收益与 FPGA 实现代价。

展示时建议使用三张主图突出结论，本文档则保留原始数值、派生指标、实验环境和计算口径，供制作图表和答辩追问时备查。

## 1. 指标与计算口径

### 1.1 基本指标

| 指标 | 定义 | 主要用途 |
| --- | --- | --- |
| `cycles` | benchmark 测量区间内经过的系统时钟周期数 | 衡量完成固定任务的总成本 |
| `instret` | benchmark 测量区间内的已执行/提交指令数 | 衡量动态指令数量 |
| `mem_wait` | CPU 数据请求等待 `mem_ready` 的累计周期数 | 判断数据访存等待是否显著 |
| `wait %` | `mem_wait / cycles` | 观察数据口等待在总周期中的占比 |
| CPI | `cycles / instret` | 衡量平均执行一条指令需要多少周期 |
| cycle speedup | `baseline cycles / optimized cycles` | 衡量完成同一任务的相对加速 |
| 指令吞吐量 | `clock frequency / CPI` | 比较执行相同指令流时的核心效率 |
| workload 吞吐量 | `workload size × clock frequency / cycles` | 衡量每秒完成多少实际工作 |
| 运行时间 | `cycles / clock frequency` | 把周期数换算为实际时间 |

`cycles`、`instret` 和 `mem_wait` 均在 firmware 的 `perf_begin/perf_end` 测量区间内统计，不包含初始化、结果校验和 UART 打印。

### 1.2 时钟频率的三个概念

| 概念 | 当前项目中的含义 |
| --- | --- |
| 板载输入时钟 | TEC-PLUS 板卡提供 50 MHz 时钟 |
| 目标/实际运行频率 | 当前 ISE 工程按 20 ns 周期约束，并在板上以 50 MHz 运行 |
| `Fmax` | post-route timing 根据关键路径估计的最高安全频率，不一定恰好为 50 MHz |

ISE 中 `slack >= 0` 表示满足当前 20 ns / 50 MHz 约束；若报告给出最小可实现周期，则可用 `Fmax = 1 / minimum period` 估算最高频率。

### 1.3 使用限制

- PicoRV32 与 DarkRISCV 的 wrapper/ACK 时序不同，跨核比较应优先使用相同 workload 的 `cycles` 和 CPI，不把两核的绝对 `mem_wait` 当作完全相同的停顿定义。
- 同一颗核在 BRAM 与 SDRAM 之间的 `mem_wait` 和 `wait %` 变化可以用于定位存储瓶颈。
- `KIPS @ 1 MHz` 是仿真 testbench 在 1 MHz 参数下的等效指令吞吐量，不是开发板频率。
- 对不同 ISA 或不同动态指令数量的实现，例如 scalar 与 DOT4，不能只看 CPI，应优先比较 workload 吞吐量和总运行时间。

## 2. 三张主图的数据底表

### 2.1 主图一：流水线 DarkRISCV 与多周期 PicoRV32

PicoRV32 是小型多周期基线，DarkRISCV 是三阶段流水线、单发射、顺序执行核心。两者运行在相同 MiniSoC 外壳、memory map 和 firmware 口径下。

| workload | Pico cycles | Pico instret | Pico CPI | Dark cycles | Dark instret | Dark CPI | Dark cycle speedup |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| ALU dependency | 151655 | 24592 | 6.167 | 65596 | 24592 | 2.667 | 2.31x |
| Branch alternating | 157804 | 26641 | 5.923 | 86078 | 26641 | 3.231 | 1.83x |
| BRAM load/store | 64610 | 10255 | 6.300 | 32826 | 10255 | 3.201 | 1.97x |
| Mixed | 214747 | 35956 | 5.972 | 100740 | 35956 | 2.802 | 2.13x |
| System stencil BRAM | 115072 | 18333 | 6.277 | 57046 | 18333 | 3.112 | 2.02x |
| Median BRAM | 34853 | 4942 | 7.052 | 22672 | 4942 | 4.588 | 1.54x |
| Memcpy BRAM | 208185 | 32031 | 6.499 | 128106 | 32031 | 3.999 | 1.63x |

推荐图形：以 workload 为横轴、Dark cycle speedup 为纵轴画柱状图，并在柱顶标出 Pico/Dark CPI。这样倍率负责表达结论，CPI 和原始数据仍可追溯。

以 Mixed 为例，若两颗核都按共同的 50 MHz 频率运行：

| CPU | CPI | 50 MHz 下的估算指令吞吐量 |
| --- | ---: | ---: |
| PicoRV32 | 5.972 | 8.37 MIPS |
| DarkRISCV | 2.802 | 17.84 MIPS |

这里的 `50 MHz` 结果是按共同频率进行的换算，用于说明 `frequency / CPI` 的关系；严格比较两颗核各自的最大吞吐量，还需要取得各自同口径的 post-route `Fmax`。

#### 结论

- 相同 workload 的 `instret` 一致，cycle/CPI 差异可以主要归因于核心执行方式。
- DarkRISCV 在计算和 BRAM workload 上获得约 1.54x～2.31x 的 cycle speedup。
- ALU dependency 的收益高于 branch alternating，符合流水线在分支跳转时需要处理 flush 和控制冒险的特征。
- 项目没有自行设计完整五级流水线 CPU；准确表述是“引入并适配三阶段流水线 DarkRISCV，在同一 SoC 中与多周期 PicoRV32 进行量化对照”。

### 2.2 主图二：真实开发板上的 BRAM 与 SDRAM 性能差异

以下数据均来自 DarkRISCV 真实开发板 UART benchmark。`SDRAM / BRAM cycles` 越大，表示外部存储对该 workload 的影响越显著。

| workload | BRAM cycles | SDRAM cycles | BRAM CPI | SDRAM CPI | BRAM wait % | SDRAM wait % | SDRAM/BRAM cycles |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| System stencil | 54966 | 125908 | 3.176 | 7.275 | 29.6% | 72.3% | 2.29x |
| Median | 23350 | 51312 | 4.162 | 9.148 | 27.4% | 69.9% | 2.20x |
| Memcpy | 128126 | 261822 | 3.999 | 8.173 | 25.0% | 66.2% | 2.04x |
| Memset | 22654 | 37230 | 4.392 | 7.218 | 18.2% | 53.0% | 1.64x |
| Stride read-modify-write | 90176 | 155722 | 2.751 | 4.750 | 18.2% | 55.3% | 1.73x |
| CRC32 | 655428 | 729638 | 2.581 | 2.873 | 2.5% | 13.0% | 1.11x |

推荐图形：以 workload 为横轴画 `SDRAM/BRAM cycles` 柱状图；可用柱内或副轴补充 SDRAM `wait %`，不要只保留倍率。

#### 结论

- System stencil、Median 和 Memcpy 的 SDRAM cycles 超过 BRAM 的 2 倍，且 SDRAM `wait %` 达到约 66%～72%，说明数据访存是主要瓶颈。
- Memset 与 Stride 的 SDRAM 惩罚约为 1.64x～1.73x，仍明显受外部存储等待影响。
- CRC32 包含大量位运算，计算成本占主导，因此从 BRAM 换到 SDRAM后只增加约 11%。
- Stride 1/2/4/8/16 结果几乎相同，因为当前 controller 无 Cache、无 burst、无 line buffer，且每个 case 执行相同数量的独立 word 事务。

### 2.3 主图三：DOT4 scalar 与 custom-0 指令

DOT4 benchmark 固定执行 `32 vectors × 16 rounds = 512` 个 signed INT8 四元素点积。scalar 与 custom 使用相同输入，checksum 均为 `0x00000170`。

#### 原始板级数据

| 模式 | checksum | cycles | instret | mem_wait | CPI |
| --- | ---: | ---: | ---: | ---: | ---: |
| RV32I scalar | `0x00000170` | 694304 | 242721 | 22548 | 2.861 |
| custom DOT4 | `0x00000170` | 25760 | 6721 | 6164 | 3.833 |

#### 派生性能指标

| 指标 | Scalar | Custom DOT4 | 改善 |
| --- | ---: | ---: | ---: |
| cycles | 694304 | 25760 | 26.95x cycle speedup；总周期减少 96.29% |
| instret | 242721 | 6721 | 降至原来的 1/36.11；动态指令减少 97.23% |
| mem_wait | 22548 | 6164 | 降至原来的 1/3.66；等待周期减少 72.66% |
| 50 MHz 运行时间 | 13.886 ms | 0.515 ms | 26.95x |
| 点积吞吐量 | 36.9k dot products/s | 993.8k dot products/s | 26.95x |
| INT8 MAC 吞吐量 | 0.147 MMAC/s | 3.98 MMAC/s | 26.95x |
| 指令吞吐量 | 17.48 MIPS | 13.05 MIPS | 不适合单独判断任务性能 |

这里把一个四元素 DOT4 记作 4 个 INT8 MAC。若报告使用“operation/s”，必须提前说明一个 MAC 是按一次乘加还是按两个算术 operation 计数；为避免歧义，正文优先使用 `dot products/s` 和 `MAC/s`。

推荐图形：主图画 cycles、instret、mem_wait 的下降倍率，旁边保留 scalar/custom 原始值；中央重点标注 `26.95x cycle speedup` 和 `993.8k dot products/s @ 50 MHz`。

#### 为什么 DOT4 的 CPI 更高但任务更快

Custom DOT4 的 CPI 为 3.833，高于 scalar 的 2.861，但它把四组乘法与求和压缩为一条 custom 指令，使动态指令数从 242721 降到 6721。CPI 只表示“平均每条指令需要多少周期”，不能表示每条指令完成多少有用工作。因此比较不同 ISA 时，应以完成固定 workload 的 cycles、运行时间和 workload 吞吐量为主。

## 9. 性能瓶颈分析与优化路线

| 观察 | 数据证据 | 瓶颈判断 | 优化方案 |
| --- | --- | --- | --- |
| DarkRISCV 在相同 `instret` 下 cycles 更低 | Mixed 2.13x、ALU 2.31x | 多周期核心的执行效率限制 | 使用三阶段流水线 DarkRISCV 主线 |
| Branch speedup 小于 ALU | 1.83x vs 2.31x | 分支 flush/控制冒险削弱流水线收益 | 分支预测属于远期方向；当前保持简单可验证结构 |
| BRAM → SDRAM 后 CPI 和 wait % 大幅上升 | System 2.29x，SDRAM wait 72.3% | 外部存储往返成为系统级主要瓶颈 | 寄存器滑动窗口、BRAM 分块、减少重复读取 |
| Stride 1～16 几乎相同 | SDRAM cycles 均约 155712 | 当前无 Cache/burst/line buffer，每个 word 近似独立付费 | 软件 line buffer；后续再评估 burst/DMA/cache |
| CRC32 的 SDRAM 惩罚较小 | 1.11x，SDRAM wait 13.0% | 位运算计算量掩盖部分存储延迟 | 优先优化真正访存密集的 workload |
| DOT4 动态指令数大幅下降 | 242721 → 6721 | scalar 指令序列是点积内核主要成本 | custom-0 DOT4 合并四组 INT8 乘加 |
| DOT4 资源余量较小 | Slice 92%、RAMB16 100% | FPGA 面积/存储资源成为继续扩展的限制 | 收口现有功能，不继续堆叠大型 RTL 模块 |
| DOT4 Fmax 仅略高于运行频率 | 51.68 MHz vs 50 MHz | 关键路径时序余量较小 | 后续改动必须重新进行 post-route timing |

### 推荐答辩表述

> 项目首先在同一 MiniSoC 中引入三阶段流水线 DarkRISCV，并以多周期 PicoRV32 为 baseline，通过相同指令流下的 cycles 和 CPI 证明流水线收益。随后 BRAM/SDRAM 对照实验表明，核心加速后系统瓶颈转移到外部存储：访存密集 workload 的 SDRAM wait 占比达到约 53%～72%。因此软件层优先采用寄存器复用、32-bit 对齐访问和 BRAM 分块，硬件层后续才考虑 burst、DMA、line buffer 或 Cache。对于 INT8 点积，DOT4 custom 指令通过减少动态指令数量，使固定 workload 的板级吞吐量从约 36.9k 提升到 993.8k dot products/s，同时仍满足 50 MHz timing，但 Slice 与 BRAM 资源已经接近上限，体现了性能、频率和面积之间的权衡。
