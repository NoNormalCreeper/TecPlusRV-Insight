# 项目任务说明 v2：TecPlusRV-Insight

## 1. 项目名称

**TecPlusRV：基于 TEC-PLUS 的资源受限 RISC-V SoC、存储层次与轻量级数据处理加速平台**

## 2. 项目背景与定位

本项目选择课程题目 B：**基于 FPGA 开发板的处理器设计**。课程要求题目 B 在 FPGA 平台上完成处理器设计，支持 RISC-V/MIPS/自定义 ISA，可选平台包括 TEC-PLUS；基础层次要求 CPU 能运行简单测试程序，进阶层次要求集成内存和 I/O，拓展层次要求进行性能优化、自定义扩展、Cache/存储层次或 PPA 权衡分析。

本项目原计划基于 Nexys4 DDR，后因平台不可用迁移至 **TEC-PLUS**。迁移后项目不降级为简单 LED/模型机实验，而是将重点调整为：

```text
资源受限平台上的完整 SoC 设计
+ 开源 RISC-V CPU 核审阅与裁剪
+ BRAM/SDRAM/Flash/EEPROM 存储层次
+ UART/GPIO/显示类外设
+ 裸机 C 软件栈
+ 自动化仿真验证
+ 性能计数与 PPA 权衡
+ 轻量级数据处理 / TinyAI 加速扩展
```

TEC-PLUS 核心板本身提供 Spartan-6 XC6SLX9-2FTG256 FPGA、两片 HY57V2562 SDRAM、16Mbit SPI Flash、4Kbit IIC EEPROM、50MHz 晶振、CP2102 USB-UART、4 个 LED、4 个按键、复位/配置按钮和多组扩展连接器。 这意味着它虽然资源比 Nexys4 小，但仍然足够支撑一个“资源受限 SoC + 存储层次 + 外设 + 性能分析”的项目。

# 3. 项目总体目标

## 3.1 基础目标：RISC-V CPU + BRAM + UART/GPIO 闭环

完成一个能在 TEC-PLUS 上运行的轻量级 RISC-V SoC。CPU 优先采用 **PicoRV32 minimal 配置**，若资源或 ISE 兼容性不满足，则切换为自研 RV32I 子集多周期 CPU 或更小的开源 RISC-V core。

基础系统包括：

```text
1. PicoRV32 minimal / RV32I 子集 CPU。
2. BRAM boot memory，用于存放启动程序和小型 firmware。
3. TinyBus / MMIO 地址译码器。
4. UART TX，尽量支持 RX。
5. LED / KEY / test_exit 基础外设。
6. 裸机 C 程序运行环境。
7. 本地仿真 pass/fail 机制。
8. ISE14.7 综合、布局布线和板级下载验证。
```

基础验收现象：

```text
上板后 CPU 从 BRAM 启动；
UART 输出 TecPlusRV boot log；
LED 显示 PASS / FAIL 状态；
firmware 能完成 ISA smoke test、BRAM test、MMIO test。
```

------

## 3.2 进阶目标：完整小型 SoC 与存储层次

在基础 CPU 系统上扩展完整 SoC 能力：

```text
1. 统一 TinyBus 外设接口。
2. UART console。
3. performance counter：cycle / instret / mem_wait。
4. SDRAM standalone tester。
5. SDRAM 映射到 SoC 地址空间，作为数据区或 benchmark buffer。
6. EEPROM 作为配置持久化存储。
7. SPI Flash 作为 bitstream 固化或程序镜像探索。
8. 大板显示类外设：数码管 / VGA / 交通灯 / 蜂鸣器中选择若干接入。
```

存储层次规划：

```text
BRAM：
  boot ROM、小型程序、关键测试代码、异常/错误处理代码。

SDRAM：
  大数组、benchmark 数据区、可选 heap/stack、可选程序运行区。

SPI Flash：
  bitstream 固化、可选 firmware 镜像存储。

EEPROM：
  小型配置参数，例如启动模式、benchmark 参数、上次测试结果。
```

SDRAM 不作为基础闭环依赖。先独立完成 SDRAM tester，再考虑接入 SoC。这样可以避免“CPU 还没跑起来，就被 SDRAM 控制器卡死”。

------

## 3.3 拓展目标：轻量级加速、PPA 和系统可观测性

拓展目标尽可能多列出，实际完成时按时间裁剪。

优先级从高到低：

```text
1. POPCOUNT / Hamming distance 加速器。
2. DOT4 INT8 加速器。
3. CRC32 / checksum 加速器。
4. BRAM vs SDRAM 访存性能对比。
5. PicoRV32 参数裁剪前后资源/性能对比。
6. MMIO accelerator 与软件 baseline 对比。
7. UART bootloader。
8. Trace buffer / debug monitor。
9. VGA 性能面板。
10. EEPROM 保存配置。
11. Flash 固化启动镜像。
12. 小范围 assertion / 协议一致性检查。
```

# 4. 早期探针测试

探针测试不是项目亮点，而是**最先做的风险排查**。它们的目标是尽早确认平台、工具链和关键外设是否可用。

由于 ISE 和板卡主要在实验室，探针必须满足：

```text
1. 每个探针独立 top module。
2. 每个探针独立 UCF。
3. 每个探针有 README，写清预期现象。
4. 实验室中可以快速综合、下载、判断成功/失败。
5. 能本地仿真的模块必须先本地仿真通过。
```

## Probe 0：LED / KEY / RESET / CLK 烟测

目标：

```text
确认 ISE 工程可建；
确认 UCF 管脚绑定正确；
确认 JTAG 下载正常；
确认 CLK、RESET、LED、KEY 可用。
```

预期现象：

```text
复位时 LED 全灭；
复位释放后 LED 跑马灯；
按 KEY1 改变闪烁速度；
按 KEY2 切换显示模式。
```

TEC-PLUS 引脚文档给出核心板 CLK 为 T8、RESET 为 L3，LED4–LED1 为 L12/L13/M13/M14，KEY4–KEY1 为 P11/T12/R12/T13，按键常规约 2.75V、按下约 0.15V。

## Probe 1：UART TX / Echo

目标：

```text
确认 CP2102、串口引脚、波特率、PC 串口工具可用。
```

预期现象：

```text
上板后周期性发送：
Hello TecPlusRV

可选：
PC 发送字符，FPGA echo 回传。
```

TEC-PLUS 使用 CP2102 做 USB-UART，FPGA 侧 UART 引脚为 RXD D5、TXD D6；使用指南中的 UART 示例会周期性发送 `HELLO TEC-PLUSV3.0`，并支持接收后回传。

## Probe 2：PicoRV32 minimal 综合探针

目标：

```text
确认 PicoRV32 minimal + 小 BRAM + UART/GPIO 在 XC6SLX9 上能否放得下。
```

建议配置矩阵：

```text
A. PicoRV32 minimal + test_exit
B. A + 64 KiB BRAM
C. B + UART TX
D. C + GPIO
E. D + perf counter
```

记录：

```text
Slice / LUT / FF / BRAM / DSP
Fmax 或 timing slack
ISE warning / error
是否需要进一步裁剪
```

PPT 中 TEC-PLUS 平台对应 Spartan-6 XC6SLX9，资源为 9,152 个逻辑单元、576Kb 内存、16 个 DSP slice 和最多 200 个 I/O，因此这个探针非常关键。

## Probe 3：本地 MiniSoC 仿真探针

目标：

```text
在不依赖 ISE 和板子的情况下，先跑通：
CPU + BRAM + MMIO + test_exit + firmware。
```

预期现象：

```text
firmware 写 0x10000030 = 1；
testbench 自动输出 PASS 并结束；
失败时输出 0xdeadxxxx 错误码；
超时则判定 TIMEOUT。
```

这个探针是本地开发的主保护线。只要本地仿真没过，就不应该去实验室烧板。

## Probe 4：SDRAM standalone tester

目标：

```text
不接 CPU，单独验证 SDRAM 控制器可用。
```

预期现象：

```text
写入固定 pattern；
读回校验；
LED 显示 RUN/PASS/FAIL；
可选 UART 输出错误地址和错误数据。
```

使用指南中说明 TEC-PLUS 的 SDRAM 为 HY57V2562，容量 256Mbit、16 位数据宽度、3.3V 工作电压，并给出“写入整个存储器、再读写对比、用 LED 表示测试进行和错误”的 SDRAM 测试思路。

## Probe 5：显示/大板外设探针

可选，用于确认展示资源：

```text
数码管 / 频率计显示区
蜂鸣器
交通灯
VGA
```

引脚定义文档中给出蜂鸣器 Spk、交通灯 TL0–TL11、VGA R/G/B/HS/VS 等外设管脚，可按实际大板连线验证。

# 5. 项目亮点

## 亮点 0：资源受限下的平台迁移与参数化裁剪

项目从 Nexys4 迁移到 TEC-PLUS，不是单纯换板，而是完成一次真实工程迁移：

```text
Vivado → ISE14.7
Artix-7 → Spartan-6
.xdc → .ucf
丰富板载外设 → 教学实验平台外设
宽松资源 → 资源受限
```

报告中要重点说明：

```text
哪些模块是平台无关的；
哪些模块需要平台适配；
PicoRV32 参数如何裁剪；
为什么保留/舍弃某些外设；
资源和时序如何影响系统规模。
```

这对应课程强调的“资源与时序约束下进行量化权衡”和“系统工程能力”。

## 亮点 1：Verification-first 自动化验证体系

这是第一主线。

目标不是“能跑”，而是：

```
每个模块有测试
每个 SoC 功能有 self-checking firmware
每次仿真能自动 PASS / FAIL
每个错误有 error code
仿真和上板尽量运行同一份 firmware
```

具体包括：

```
1. 模块级 testbench
   - UART TX
   - TinyBus 地址译码
   - GPIO/MMIO
   - POPCOUNT/DOT4 accelerator
   - SDRAM controller 或 SDRAM tester

2. SoC 级自校验 firmware
   - isa_test
   - memory_test
   - mmio_test
   - uart_test
   - accel_test
   - benchmark_test

3. test_exit 机制
   - 0x1000_0030 = 0x00000001 表示 PASS
   - 0x1000_0030 = 0xdeadxxxx 表示 FAIL + 错误码

4. signature comparison
   - firmware 写结果区
   - testbench dump signature
   - Python/C reference 生成 golden signature
   - 脚本自动比较
```

这才是“自动化验证”的亮点。不是 difftest 全量实现，而是适合课设规模的 verification-first。

------

## 亮点 2：可观测调试体系

这是第二主线。

问题是 FPGA 上没有普通软件调试器，所以要主动设计“可观测性”。

至少包括：

```
1. UART console
   - boot log
   - test log
   - error code
   - benchmark result
   - resource/profile summary

2. debug registers
   - last_pc
   - last_mem_addr
   - last_mem_wdata
   - trap_flag
   - error_code
   - current_mode

3. 板级可视化
   - LED 显示 PASS / FAIL / RUNNING
   - 数码管或大板显示错误码 / benchmark id / cycle 低位
   - KEY 切换显示模式

4. 可选 trace buffer
   - 记录最近 N 次访存或执行事件
   - 出错后通过 UART dump
```

这里的重点不是“显示好看”，而是：

> 当系统失败时，我们能知道失败在哪里；当性能变慢时，我们能看到瓶颈在哪里。

所以 LED、数码管、UART、VGA 都只是可观测性的不同出口。

## 亮点：PPA 与资源受限权衡

这是第三主线。

TEC-PLUS 换板反而强化了这个亮点。它的 FPGA 是 Spartan-6 XC6SLX9，资源明显受限；资料中也明确给出了核心板的 SDRAM、Flash、EEPROM、UART、LED、KEY 等资源。

要做的不是“我们也能跑”，而是：

```
我们如何在资源受限下选择 CPU 配置、内存规模、外设数量和加速器形式。
```

需要输出一张核心表：

```
配置                         资源占用       Fmax     cycles     CPI     说明
Base CPU + BRAM              ...           ...      ...        ...     最小系统
+ UART console               ...           ...      ...        ...     可观测性
+ Perf counter               ...           ...      ...        ...     性能测量
+ POPCOUNT accelerator       ...           ...      ...        ...     加速器收益
+ SDRAM tester/controller    ...           ...      ...        ...     存储层次
+ Trace/debug                ...           ...      ...        ...     调试能力
```

PPA 不一定真的测功耗，课程语境下可以解释为：

```
Performance：cycles / CPI / throughput / Fmax
Power：用资源与时钟频率做间接讨论，或只做定性分析
Area：Slice / LUT / FF / BRAM / DSP
```

## 亮点 3：TinyBus 插件式 SoC 架构

统一外设接口：

```verilog
input         valid;
input  [31:0] addr;
input  [31:0] wdata;
input  [3:0]  wstrb;
output [31:0] rdata;
output        ready;
```

所有外设挂成 slave：

```text
bram_slave
gpio_slave
uart_slave
perf_slave
sdram_slave
eeprom_slave
accel_slave
debug_slave
```

亮点不是接口复杂，而是说明你们把系统设计成了**可扩展平台**，而不是把所有逻辑写死在一个巨大 top 里。

## 亮点 4：BRAM + SDRAM + Flash + EEPROM 存储层次

利用 TEC-PLUS 的存储资源形成层次设计：

```text
BRAM：启动和小程序
SDRAM：大数据区和 benchmark buffer
Flash：固化配置或镜像
EEPROM：小配置持久化
```

可以做一个很有说服力的 benchmark：

```text
同一数组求和 / Hamming benchmark：
1. 数据放 BRAM
2. 数据放 SDRAM
3. SDRAM + 简单预取 / line buffer
```

比较：

```text
cycle
instret
CPI
mem_wait
throughput
资源占用
```

## 亮点 5：裸机 C SDK

完成一个小型板级支持包：

```text
startup.S
linker.ld
mmio.h
uart.c
gpio.c
perf.c
sdram.c
eeprom.c
accel.c
print_hex / print_dec / puts
```

这样展示时不是“硬编码机器码”，而是可以运行真实裸机 C 程序。

## 亮点 6：轻量级数据处理 / TinyAI 加速器

优先做 **POPCOUNT / Hamming distance**，因为它资源小、容易验证、适合 Spartan-6，也能包装成二值向量相似度 / TinyAI 分类。

可选再做 **DOT4 INT8**：

```text
rs1 = 4 个 int8
rs2 = 4 个 int8
result = a0*b0 + a1*b1 + a2*b2 + a3*b3
```

接口可以二选一：

```text
低风险：MMIO accelerator
高集成度：PCPI / 自定义指令
```

建议先做 MMIO accelerator：

```text
CPU 写输入寄存器
CPU 写 START
硬件计算
CPU 轮询 DONE
CPU 读 RESULT
```

这也能体现硬件/软件协同，不必一开始侵入 CPU 指令译码。

## 亮点 7：性能计数器与 PPA 分析

实现：

```text
cycle counter
instret counter
mem_wait counter
accel_active counter
```

最终至少形成这张表：

```text
配置              Slice/LUT/FF/BRAM/DSP     Fmax     cycles     CPI     speedup
Base SoC
+ UART
+ Perf
+ SDRAM
+ POPCOUNT
+ DOT4
```

课程评分强调硬件资源利用效率、系统运行状态、调试效果、问题分析能力和附加功能创新性；这张表能直接服务答辩。

## 亮点 8：显示类演示程序

根据时间选择：

```text
1. UART console：主展示。
2. LED/KEY：模式选择和状态显示。
3. 数码管/频率计显示区：显示 cycle / 错误码 / benchmark 结果。
4. VGA：显示 TecPlusRV 状态面板或性能条形图。
5. 交通灯 / 蜂鸣器：作为 MMIO 外设展示。
```

不要让这些展示压过 SoC 主线。它们的定位是证明 **CPU 可以通过 MMIO 控制真实外设**。

# 6. 推荐最终演示流程

```text
1. 下载 bitstream。
2. UART 输出：
   TecPlusRV booting...
   CPU: PicoRV32 minimal
   Memory: BRAM + SDRAM
   UART: OK
   GPIO: OK

3. 运行基础测试：
   ISA test PASS
   BRAM test PASS
   MMIO test PASS

4. 运行 SDRAM tester：
   pattern write/read
   error count = 0

5. 运行 benchmark：
   software popcount / hamming
   hardware accelerator
   输出 cycles / instret / CPI / speedup

6. 运行外设展示：
   KEY 切换模式
   LED/数码管/VGA/交通灯显示状态

7. 展示 ISE 报告：
   Base / +SDRAM / +Accelerator 的资源与时序对比。

8. 展示调试日志：
   平台迁移、探针测试、AI/开源使用、关键 bug 与解决方案。
```
