# 开发日寄

## Day 1

课上看了下要求，查了一下相关概念和教程，感觉和我做了一点的南京大学 PA 项目和看过的一生一芯教程有很多地方重合，狂喜，感觉很有意思。

拿到了 Nexys 4 DDR 板子，看起来非常好用，摩拳擦掌兴奋地准备大干一场！结果发现唯一的一个数据烧录口用不了，换了很久跳线和供电方式都没用，找了老师发现确实是没办法了......

所以只好换成了“最烂的” Tec Plus，那个闻名丧胆的折磨了我们好久的试验箱。虽说开发上差异不是非常大，但是烧录没那么方便现代（得用 ISE 而非 Vivado），而且外设、内存之类的也退化了一节。唉！就这样吧。

想了想我想要做出的特色，开始做一层比较薄的架构，辅助大家理解我的整个项目思路。同时制作了一些“探针”们，用于最小化在实验室验证我的一些想法，因为担心后面改动越来越大难以定位问题，所以想给各层留一点自动验证的空间。

下午下载了很久的 ISE，终于在晚上把它装好了。半天没研究明白这种老的开发软件如何管理 source file，弄完之后还花了很久时间走每个流程配置和烧录，都要怀疑人生了。Program 一秒完成，但是烧录到板子上之后，发现板子上没有任何反应。于是我又花了很久时间查资料，没查出来。重启了几次软件就好了，成功跑通了 Probe 0 这个例程。

然后还花了很长时间排查串口驱动连不上的问题，最终去官网下载了驱动，导入终于成功了。然后尝试跑 Probe 1，结果发现串口输出的内容是乱码，`HloTclsV`——正好是 `Hello TecPlusV` 的每个字符隔一个丢一个。原来是初版生成的 `probe_uart_top` 里对 `ready`/`valid` 的用法错了。它原来会在 `uart_tx` 真正接收 1 个字节前，把 `msg_index` 多推进一次，所以板上就表现成隔一个字母丢一个。

这两个例子都让我早早地意识到，板子上的问题不一定是核心逻辑错误，甚至不一定是错误，可能只是各种握手、约定，甚至只是工程配置、设备状态不一致，后面出错要优先检查这些。

发现这些 Probe 都不需要大的实验箱，于是把板子拿回宿舍继续尝试 PicoRV，结果提示 design too large。吓死我了，还以为是没法引入 PicoRV 了，然后看了下报表，

```
Slice Logic Utilization:
  Number of Slice Registers:                   581 out of  11,440    5%
...
  Number of Slice LUTs:                      1,178 out of   5,720   20%
```

还以为这些数值是**超出的百分比**，仔细一看才知道是**占用的百分比**，根本没用完！实际上根因是：

```
IO Utilization:
  Number of bonded IOBs:                       317 out of     186  170% (OVERMAPPED)
```

这才知道，因为我把顶层设为了 `picorv32_axi`，这个模块暴露了很多顶层端口（我先前完全没有“顶层”这个意识），ISE 把他们都当成 FPGA 外部引脚了，所以才爆掉（超过 186 个 bonded IOB）了。于是顺手开始写一个简单的 MiniSoC 作为 top，去引用 `picorv32`。

结果还是炸了而且原因还不一样，居然是 64 KiB bram 没有被正确推断成 FPGA 的 Block RAM，被当成按位展开的 LUT RAM 了（8192）：

```
  Number of Slice LUTs:                     10,166 out of   5,720  177% (OVERMAPPED)
    Number used as logic:                    1,945 out of   5,720   34%
    Number used as Memory:                   8,216 out of   1,440  570% (OVERMAPPED)
```

给 RAM 数组加一个 `(*ram_style = "block"*)` 属性，就成功了！这次的 map 流程依旧很慢，让人安心。总算是确认了能跑 RISC-V 了！

然后和舍友进行了分工，又讲了一遍我那个最经典的 `printf` 从用户程序到串口输出的流程，虽然磕磕绊绊但感觉讲得比上次更熟悉了。希望大家确实领悟到了我想要做的东西并能领悟出（至少能知道自己写的代码往哪丢）我的~~天才~~架构设计吧。

正喜的时候发现好像没考虑流水线，进行了一些调研后觉得这个思路也挺有意思的，可以尝试：引入 darkriscv（小，三阶段流水线），不过需要引入一个小的 wrapper，改 mem 接口（双口请求）、总线接口转换等，明天早上起来研究一下，这样可以对比“同一个 SoC，两种核”的性能差异，或许比较有意思。

## Day 2

先是给队友各安排了熟悉项目用的 issue，都是比较小的改动，但要求能口头解释，让大家能理解整个项目的概念和链路。

同时还接入了 Makefile 和 GitHub Actions。虽然早期 CI 本身也不稳定，但这让测试变成了公共的契约，防止大家改坏或者提交之前忘记自己测试就推上来了。

然后花了一上午尝试引入了 darkriscv，开启了一些基础功能。不过因为接口有些不同，所以引入了两个核各自 adapter + 一个 soc cpu wrapper 的结构，成功把两个核都接进来了，可以通过开关来切换。一直在和 Agent 沟通想法，最后决定了一些权衡：

- 存储拆开成 I-bus 和 D-bus，并行但语义不同（可执行存储 和 普通外设/数据设备）
- 只有 BRAM 现在是可执行存储
- tinybus 不接入取指通路，也就是接到 tinybus 的地址块只能负责数据或 MMIO
- SoC 的取指口的状态机改变为 `ifetch_valid -> ifetch_pending -> ifetch_ready` 了

不过现在这个结构还只是中间态，后面可能还需要做到真正的 master-slave 结构，多主设备仲裁等。

这样改变了我昨天和组员沟通的心智模型（尤其是 SoC），今天还得再解释一下...

接入后，写了新的回归测试，通过后我就开始尝试进行简单（instret 的语义并不严谨，后面得改）的性能测试，发现流水线带来的差异还挺显著的：

```text
cpu          cycles       instret      cpi_x1000
picorv32     862823       156901       5499
darkriscv    404897       202448       2000
```

于是有了些许欣慰。

希望这些新增的回归测试让我这么庞大的一个修改尽量少出错吧！

下午，尝试修改性能计数器的技术路径——感觉应该不会非常困难，直接转发两颗核各自的 backing counter 就行，为了以后测试的准确性决定改一下。确实不复杂，但改着发现这样不仅需要改一些编译开关，还要添加一些输出口导出来，于是 wrapper, adpater 等也要一起改。

仔细看了一下，也可以保持不改 core，但是这样固件就需要读 CSR，这和之前的 MMIO 契约就不一样了，我希望能保持一致的契约，减轻心智负担和已经有的基础设施（毕竟整个项目时间就这几天，改契约会很麻烦），因此，为了同时满足“MMIO 地址不变、可综合、双核统一接口、验证链条简单”，只改 core 的导出口，把内部的计数值导出来，最简单最稳定。

然后我也对改动的 core 部分进行了注释，提示自己哪里是自己改的，后面不要被绕晕或者改回去。

新的 perf 输出看起来合理了一些：

```
cpu          cycles       instret      cpi_x1000
picorv32     858661       143853       5969
darkriscv    402526       143853       2798
```

不过看了 DarkRISCV 代码内部具体的实现，感觉他仍然是近似 retire，不是严格 retire pulse 驱动的计数器，递增条件是 `if(!HLT & !(|FLUSH)) CSRINS <= CSRINS+1;` (HLT 是总线等待，FLUSH 是 pipeline flush)，虽然比之前的 SoC 计数靠谱一点，但还是一种估算。不过 DarkRISCV 自己的 simulation perf report 也是按照这个方法来算 `instr` 的，那我就把它视为性能的**估算**，先这么用着吧。后期再改成更为严谨的判断方法。

感觉差不多了，于是开始看进阶任务，我想要明天开始“SDRAM 数据区 + 最小 runtime + Bootloader v1”这个主线了，于是进行了很多头昏脑涨的调研，还发现 SDRAM 的驱动和接入似乎比想象的复杂得多，因为要考虑各种控制信号、状态转移、时序等等。不过我没有扎进去，而是换了个思路，划分了一下每一层为了干这个事情需要做什么，把 soc 层内部的复杂实现留给负责这个的队友和明天的自己吧。发了一些 milestone issue，明确了一下分工，希望他们能领悟，准备明天再讲讲，顺便看看他们对于今天的熟悉任务有什么感悟。

晚上负责上板的同学开始测试了我写的双内核切换，不知道为什么还是开始的时候诡异地 program 完之后无反应，后面多试了几次就好了。和昨天一样，串口成功输出了，但成功得不多——不一样的是今天每个字符都输出了两次。应该是同一个 store 被 SoC 顶层重复受理了两次，仿真测试居然没有测出来，但我 dump 了生成的 .vcd 文件可以看到一个 UART 字节发生了两次 uart_fire。

继续查阅发现 darkrv 的数据总线是“电平保持直到 ack”，而我顶层的状态逻辑是“请求在 ack 后立刻撤掉”，darkrv 的 D-BUS 在一次 ack 之后还把同一个 store 保持了几个周期，顶层又把它当成新请求收了一次！于是我连忙补了一个回归测试不让单次 UART 被发两次固定问题，然后在 minisoc top 里处理“重复看到同一笔已完成请求时，不该再次产生 MMIO 副作用”。本来是在 adapter 里面写，但容易不小心重写 darkriscv 的总线语义，导致卡住其他后续合法请求，所以想了下还是让 minisoc 负责了，因为这也是他的职责边界（确保不会把同一笔已完成事务执行两次），这样也更稳。

一切解决之后，我把之前写的 `perf_mix.c` 稍微改了一下从 UART 输出性能测试结果，怎么看着这数字这么眼熟...

```
perf mix started.
perf_cycle_delta: 402526
perf_instret_delta: 143853
```

居然和仿真的是**完全一致**的，想了想也挺有道理的，板上和仿真虽然“现实时间不一样”，但 RTL、程序、控制流都是一样的，这俩都只是核内计数器的值，那也当然是完全一样的。确实，这组指标只能比较 pico vs dark / 优化前 vs 优化后 / BRAM vs SDRAM 等吧。真实性能还得看频率（查了一下，这和手机电脑降频不一样，这个好像得在 ISE 上看？）。高情商：说明 counter 路径、benchmark 测量区间、导出的 firmware 都可信！

原来这里的频率和前面的 LUT / FF / BRAM 之类的指标是一样的，属于实现代价，看耗多少资源。查了一下资料，在 ISE 里的 static timing 读到 `slack = +2.397ns`，就是距 20ns 的约束 (50MHz) 的距离还有这么多，满足 timing 且留有很多余量！！这太酷了，这样就可以算出来这段 benchmark 大概多久跑完了。以后的优化也可以对这些数据进行记录，和 baseline 进行对比。给今天画上了一个略圆满的句号！

洗澡的时候就开始幻想有了 bootloader v1 后的生活了，开始想我可以往里面装些什么好玩的用户程序，回想起翻手册隐隐约约记得有 VGA 实验，我灵机一动，是不是可以结合蜂鸣器放一个 Bad Apple 的视频！我想起来之前做 PA 的时候看过一个[类似的实现](https://github.com/NJU-ProjectN/am-kernels/commit/7bb7b1a94fb13729dcc8ce4b384fff47caeb04ec)，回来看了下源代码，他这个应该是 80x25 1-bit 的终端字符画配合音频接口，那我大概可以写一个简单的字符或者 tile 模式的 rtl 传过去，不用 framebuffer。具体实现还没看，不过应该是可以实现而且使用 MMIO 接口的吧。后面再去看看，只要把这些基础设施做好了，以后就是加一个外设+用户程序的事。

听负责上板的队友说 probe 4a 和 4full 都基本成功了，看来 SDRAM 的成功和失败路径、状态流转等都是可用的，太好了！

## Day 3

今天准备去实际的实验箱上试一下外设的 probe 5，和新增的 VGA probe。

上午增加了 ISE 工程自动导出脚本，ISE 的 source 管理略有折磨，所以我想把手工导入、选 top、添加依赖的流程脚本化一下，这样就能直接从文件夹里复制粘贴了，以后也更方便了。

下午到了实验室，先进行交通灯的尝试，结果半天什么都点不亮，只有板子自带的流水灯（我们设计用于标注板子活着的心跳包）在动。后面仔细看讲义表格的绿色部分，结合在实验箱上细致的观察，我才知道，原来板子的排针插到实验箱里，并不是自动就连接到外设了，而是还要从实验箱的排针用排线连接到对应的外设区域排针上才能正常运行！

于是连上了还是没亮，十分疑惑，排查了半天 probe 代码的问题（之前也出现过代码写得不符合约定的问题），结果没找到。

然后我就开始尝试用一些硬件的 debugger。我首先把目光盯上了桌子上放的示波器，拿笔一头插到实验箱上突出的排针（后面经过指导才知道这样很危险容易短路，用母杜邦线代替了），另一头夹在共地，发现示波器没什么动静，只有干扰的波形，但是实验箱上的时钟是能正常显示的。查了一下才知道因为我们的信号周期太长，5s 左右才回到初始状态（毕竟本身设计是给肉眼看 LED 灯的），示波器看不出来。

于是我准备拿万用表看电压手动判断，结果万用表没电池... 心灰意冷之际才想起来数电实验用过的“逻辑笔”，可以指示高低电平。测了下发现板子是有正常输出高低电平的。

更困惑了，不知道是哪里的问题，后面索性直接用逻辑笔测过的能输出高电平的开关直连交通灯，结果还是没反应。此时我甚至怀疑是驱动方式有什么问题（甚至都想要拿 VCC 接个电阻去持续输出电流试试），或者有什么使能信号没送出去。

实在没办法问了下老师，才知道原来是跳线没接——这是新的实验箱，没有跳帽，自然我也就没发现要接跳线。而且跳线的丝印是 `DZ`，完全没想到这是什么，第一天短暂用的 Nexys4 板子的跳线是 `JP`~~（显然更符合直觉吧）~~，所以不认识 `DZ`。接上之后直接就好了，什么问题都没有了。不过跳线这种三个引脚突出来的结构也很有特点啊，我怎么就没想到呢...

然后就去试了下 VGA thin probe，也是一下子就成功显示了彩条，甚至不需要跳线。我当初还想着 VGA 比交通灯难调故意把他安排在后面呢。

接下来是 VGA text probe，把字模显示在屏幕上。开始也是一直无信号，后面发现又是我 ISE 工程里面设置有误，导致 top 层没引入别的依赖，修复就好了，成功显示了文字。字模相关数据是 AI 生成的，没想到还挺像样，就是老电脑 BIOS 的那种字体。热泪盈眶，感觉可以做很多东西了。

最后才测蜂鸣器，测试程序里我增加了用 UART 输出音符名称，确保板子还在跑，便于定位到底是哪一层的问题。说明文档里说蜂鸣器要接 9 个口，`Spk` 和 `S8...S1`，太诡异了，半天没找到往哪接，而且觉得这么多信号口很反直觉。试了一堆能插 8 个排针的地方也没用。最后把 `Spk` 信号单独接到圆孔里，就能发声了。感觉这个圆孔和 FPGA 板子的排针都不是一个体系的东西，用的线也不一样，只好强行接起来了，以后用的时候注意。

今天听到很多人开发的时候的时序逻辑有点问题。我也想到我自己的这个核只是引入了开源项目，似乎还没进行完备的测试，决定过两天去把官方的 `riscv-test` 测试集摘取自己实现的部分拉上来测一下。可能得写个批量测试的工具，或者等 bootloader v1 出来再说。不过目前看起来是问题不大的！

晚上大致接了一下官方的 test，先跑了仿真确认了实现大致没有问题。不过值得注意的是 PicoRV32 核好像是不支持 `fence` 语义的，后面得注意这个约定。

同时发现前面的测试都非常散乱在 Makefile 里，每个模块都是散开无秩序的，以后不好拓展，而且过一会就不记得上一部分的测试命令（target 名称）了。于是我痛定思痛重构了测试方法，用一个 json 文件来管理所有测试，抽象为几种类型的测试命令，然后每次加一个新测试只用在 json 里加一条记录就行了，最后用一个 Python 脚本来跑测试，再接入到 Makefile 的一个统一的目标里即可。

## Day 4

上午在干别的活，无暇顾及。中午去找老师汇报了一下，获得了鼓励。

下午负责 SoC 的同学写了 SDRAM，但覆盖面不够，我给他补了几个 issue 中提到过的更全面的测试用例，果然仿真就报错了，于是我推了上去让他改，他一行就改好了。

他继续去写后面的了，我总觉得可能还有点风险，结合上午听闻的“很多同学今天第一次上板测试，结果发现自己代码出错根本找不出来”的悲痛经验，我决定再写一点上板测试的用例，覆盖一下他写的 SDRAM 驱动全流程。板子被写外设的同学拿走了，他晚上也写了很多东西，把缺的外设基本都接入了，就差我的 VGA 了，这块我还想好好设计一下。

洗完澡拿回来板子，我就开始测我的上板用例，果然出现了一点问题！一运行 LED 就全红了！（这是我们测试框架约定的 `FAIL` 标记。）看串口输出，case 6，`refresh under continuous req_valid` 出问题了，控制器没有在 `req_valid` 压力窗口内发出新的 refresh。进入该 case 前看到 5 次 refresh，期望至少增长到 6，实际仍是 5。仔细查看发现上面的一行修复只解决了非零 `bank/row` 的问题，而新的问题出在 `ST_IDLE` 的仲裁顺序，它先看 force_refresh，再看 req_valid，最后才看 refresh_pending。所以这个场景下已经欠下的 refresh_pending 会被饿死，出现失败。修复方式是把 `refresh_pending || force_refresh` 提到 `req_valid` 前面，保证一旦已经欠了 refresh，就先 refresh，再接下一笔请求。

本地 testbench 居然没发现这个错误（只在停止压力后检查 refresh 计数，旧逻辑会在松开压力之后补 refresh 或者 force_refresh 而通过），于是我也改了测试用例，确保新的通过，错的失败，固定回归测试。

改完之后，串口和 LED 果然输出了代表 PASS 的 `1000`，可以认为完成 M2a 的板级验证了。

但是负责这块的队友告诉我，这个修改其实并不是事实性错误，而是他自己内部的语义的约定，而刚刚的修改打破了语义的规定，应该遵循原有的语义，他经过一通调整之后，同样解决了问题。问题不只是把 `refresh_pending` 粗暴提到请求之前，而是需要同时保留控制器原本的延期语义，并保证连续请求不能让 refresh 永久饥饿。

## Day 5

把已经上板调试好的 data-only SDRAM 集成到了 minosoc 中，并用负责固件的同学写的简单测试（访问大地址内存，我在 memory map 里设置其为 SDRAM 部分），没有问题，这样证明 SDRAM 集成是成功的。跑了一些其他刻意使用 SDRAM 内存空间的测试，也一切正常。

然后便开始实现 bootloader v1，这个真的太重要了，提升开发和测试效率。这个写起来是 one-shot 的，集成到硬件上的逻辑并不复杂，就是 RST 之后接管 UART 串口，发一个 `READY` 等待，识别到协议 magic 后接受，存到 BRAM `0x0` 的位置，然后交还控制权给 CPU 即可；host 工具同理，接受到 `READY` 后按照协议传字节流，结束后等待 `ACK`，则释放串口。后面发现自己再去开串口监视器可能有点麻烦，于是加了个参数，在传输完程序后原地打开串口监视器。

因为在 WSL 下开发，开始的时候还尝试用 usbipd 把串口 bind 成 WSL 里面能直接访问的 `/dev/ttyUSB0`。后面发现 bind 之后 Windows 端又访问不了，还得 detach，太麻烦了。于是就全部跑到 Windows 上用，包括 bootloader 传程序，因为脚本是 Python 写的所以是无缝切换的，在 Makefile 里用 Windows Interop 直接调用就行，几乎原生。

接下来就是尝试驱动 VGA 屏幕和字模了，花了不少的时间去做外设和 SoC 控制的部分。我以播放有声音的 Bad Apple 剪影动画这个综合任务为目标，遇到了两个问题：

- 首先是大块的数据要存到 SDRAM 中，我起初以为这是非常自然的行为，但是链接脚本告诉我：这些数据只是**运行地址**在 SDRAM，**加载地址**实际上是在 BRAM 的，启动时由 `startup.S` 搬运过去的，所以大小还是会受到 BRAM 影响。但是运行时申请的内存会由 bump allocator 直接在 SDRAM 上申请。我想了想决定拓展 Bootloader 协议命令（我在请求帧预留了一个 `command` 字段），在传输初始程序的时候也把需要用的 SDRAM 初始大数据传过去，两阶段完成后才释放 CPU。第一版我还是先只做整包的 ACK 和整包重传，先不需要太大的分 chunk 校验和重传。实现之后上板验证又遇到了问题，大包会超时，解决了握手和一些 refresh 的问题后修复。我本来只是想在板子的硬件上实现一下拓展命令，设计好之后让 Agent 去实施，没想到他把客户端也顺手拓展了，这块我本来是想留给做固件的队友做的。

另外，现在 9600 的波特率有点慢了，这个波特率是我看讲义上的示例程序设的，不知道为什么选这个而不是常见的快一点的 115200，打算让组员做一下实验能不能改为这个快的，不然到时候传大片的数据要慢死了。

- 其次是 VGA 的驱动，计划是通过 ASCII + 一些算出来的最需要的自定义字模实现显示图片。但我艰难地写完了外设和计算字模的脚本后，在 ISE 里综合的时候出现了严重的 LUT 资源不够问题，显示用了百分之三百多，仔细看了一下发现并不是操作失误，而是真的 VGA 文字这套逻辑太耗费逻辑门了，真的没办法，这个外设接入不是像 probe 一样简单的。综合权衡计算之后，决定还是回退到最简单的像素方案，MMIO 直接写一个 64x48 矩阵，控制屏幕上的 1 位像素们。

由于 Bad Apple 的暂告一段落，加上实验室关门了，我开始进行继续的理论探索，我发现我之前思考的这个综合任务的“多外设任务并行”模型有点粗糙，自然而然地我就开始考虑 FreeRTOS 这一套的接入。它会依赖一些中断请求的机制，这也正是我后面想做的 gdb stub 所需要的。调研之后我发现他们共同依赖 machine-mode trap、timer interrupt、trap frame 基础设施，我决定先以这一套二者共用的基础设施为目标。

同时，因为我们这个进阶主线的实现也差不多结束了，我开始考虑一些量化分析性能瓶颈、提出优化方案的工作。我大致以双核交叉对照为目的，设计了微架构（ALU、分支、BRAM 等）、用户程序（滑动窗口在 BRAM 和 SDRAM 的差距）、官方 workload（排序算法和连续大块数据的访存）上进行了性能对比，自动化生成表格，大致能得出结论：Dark 在计算和 BRAM 访问上明显更快；两颗核都被 SDRAM 拖慢；后续优化应该优先减少 SDRAM 往返。

这个结果其实是符合预期的，因为现在只是接入了 SDRAM，还没有做任何的优化。有一些比较明显的问题我也顺手改了，比如我把 `memcpy` 和 `memset` 从逐 byte 操作改为了“前后处理未对齐 byte、中间按 32-bit word 操作”，这是一个非常明显的没有匹配当前 32-bit 接口的问题。

不过由于时间原因只是进行了仿真，过段时间再进行上板实验吧，结果应该是差不多的，之前的实验也已经证明了。

还有一些实验可能后续也打算做，比如我看到 DarkRISCV 上游有 Dhrystone 测试结果，可以移植过来看看我的 soc 接法有没有拖慢它。还听说有个实验叫 Embench-IoT，选取了嵌入式设备比较常见的一些测试场景，不过移植难度可能较高，作为有余力的备选。

当前我还是对中断和 RTOS 比较感兴趣，我确实一直对于这些概念迷迷糊糊的，趁着这次实践机会尝试搞懂吧。

同时我还做了一套自动做性能测试的工作流，用于后续的性能测试和瓶颈分析，不过只是仿真跑了一版结果，过两天再上板：

## Day 6

今天实验室不开，所以我的重点就转向了“先做 IRQ 相关，然后基于此移植 RTOS，最后再用 Bad Apple 程序来演示 RTOS”。

不过在一次常规的 bootload 中，突然出现了传不进去的问题，我用不同的 payload 长度试了下，发现似乎是太长导致的。原先的 Bootloader SDRAM 测试只写了 2 个 word，数据太短，根本不需要 refresh，所以一直看起来没问题。把测试扩展到了 68 个 word 时，传输会跨过 refresh 窗口，就能稳定复现了超时。当时能看到请求卡在 ready=0、valid=1，说明 Bootloader 和 SDRAM controller 对 ready/valid 的理解没有对齐。最后把 Bootloader 请求也改成和 CPU 通路一致的 ready-first 语义，问题就解决了。这又是一个前面也发生过的简单 smoke 测试无法覆盖时序边界的问题。

接下来是恶补 trap 和 interrupt 等相关知识，调研发现只有 DarkRISCV 比较合适接入，因此我把 PicoRV32 定位为用于提供性能 baseline 的简单核，而把 dark 作为我后续这些拓展的目标。我原先以为 DarkRISCV 的中断支持大部分只是打开编译开关，真正接入后才发现，除了 core 配置，还要统一 trap frame、异常入口、`mepc`/`mcause` 等 CSR 语义、machine timer、固件 runtime 和 SoC 顶层连接。实现完之后，上板一遍测试（从 timer 进入 trap、保存上下文、执行 handler，再返回原程序）通过，但我保持了谨慎，因为这是自己不那么熟悉的语义，而且最近出了太多一开始看起来正常后面出问题的测试了。

完成验证后，我决定把支持 IRQ 的 DarkRISCV 路径作为后续主线，不过不用中断的普通程序仍然可以照常运行，正如之前所说，PicoRV32 保留为简单可靠的性能 baseline。

万事俱备，接下来就是实现昨天决定的大幅度削减的 VGA bitmap MMIO 了，忍痛控制范围，实现完后接入 MiniSoC 然后进行综合，结果还是提示无法满足约束，LUT 占用居然还是 151%！不过仔细看了后才知道是和当时 BRAM 的问题有点像，二维数组等没有被推断成 RAM，而是变成了寄存器和 LUT，我改写为同步写入、单独异步读出的形式就恢复正常，能正常综合了。

想了下，FreeRTOS 应该设计为可以复用的一个 profile，能在多个独立 demo 程序中复用，而 bad apple 是其中最复杂的一个，全面展示我们的多任务能力。

我本以为直接把上游 release 搬进来，“接一下线”就差不多了，但实际上还需要自己写一层。上游提供的是具体 CPU 无关的调度内核，但我们的内核进入 trap、保存寄存器、machine timer 等方法，他并不知道，这也是我们自己的内部约定，所以需要写一个 port：构造初始 trap frame，写 trap entry 的逻辑（保存、恢复寄存器等）、转化 IRQ 到 tick、实现 yield 等，做一个适配层。这块我也不太理解，磕磕绊绊在 AI 的辅助下完成的。

晚上开始把 Bad Apple 真正接入进这个 RTOS，计划在本地从原始视频生成动画和音频数据，上板的时候用拓展的 bootloader 把这些大块的数据放进 SDRAM 里。

视频的数据倒是很好生成，用 ffmpeg 做一些采样即可，本来也就是剪影动画，效果是可以保证的。但音频就没那么容易了，最初是从原视频提取音频压成单声道方波，但非常难听。于是我想到了用 MIDI，开始在网上找了一个非常华丽的 MIDI 音频资源，各个声部和乐器配合良好，电脑上听感非常棒，但实际上的蜂鸣器一个时间点只能播放一个频率，于是进行了各种轨道叠加或者取其中一个轨道的尝试，效果都不尽人意，总是有几段不合适，而且最后发现和视频的音频不是完全契合的。后面我改变思路找了个比较简单的钢琴旋律版本，同时特殊处理开头的低频率鼓点和贝斯声的部分，终于得到了比较好听的一版，决定明天上板实测。同时值得一提的是因为没有到实验室测试，所以我最开始就写了个本地生成一个视频模拟最终显示和蜂鸣器声音的脚本，为调试省了很多时间。

这样下来，资源大小几乎达到 1 MiB 了，负责串口的同学也把波特率提上去了，我还给 bootloader 脚本添加了显示实时上传进度的功能，整个链路已经完全打通，万事俱备只差明天的实测了！

## Day 7

一大早起来去实验室测了下 Bad Apple 全流程，最开始我先拿了几个简单的 VGA 固件来看有没有初步的问题，发现屏幕上显示的是被拉宽的矩形，发现似乎是显示器比例问题，显示器还被锁定了，我在网上查到文档后解锁，把显示比例从 16:9 改为 4:3 就是正常的小正方形了。

修正后就成功开始播放了！画面和声音都正常！但是播放到 109 秒的时候画面突然停止然后损坏了，蜂鸣器也卡顿在异常脉冲上，但串口仍然在输出，到了 132s 才卡住。说明并不是整个 SoC 卡死了，我推测更有可能是视频 task 或者 scheduler 或者某个运行时对象出了问题。

为了缩小问题，我增加了一些 UART 输出的诊断信息，然后还试图从 100s 开始播放，尝试复现，但并没有复现，说明问题并不是那一段视频的问题，而可能是累计运行时间过长或者偶发的调度破坏问题有关，或者是栈空间覆写等，后来还进行了一些小修小补，几乎不会出问题了，但这也只是排除了一些可能的原因，并没有真正定位问题。同时这几次更改都只是修改 BRAM 的程序，而不影响 SDRAM 的视频资源，我又给 bootloader 工具添加了一个和仅覆盖 BRAM 程序内容的参数。

后面问题几乎不会出现了，也难以复现，我就只是先留着这些诊断信息，方便下次出现问题的时候使用。

基本播放没问题之后，我就把他补充成了一个比较全面的 FreeRTOS 多任务演示，最终拆成了更新 VGA、驱动蜂鸣器、LED 打拍子、交通灯流水、按钮控制暂停的五个 task。还进行了一些优先级调整，因为有时候播放任务调用 yield 的时候，只把 CPU 让给了同优先级任务，没法让更低优先级的 LED 和交通灯也获得运行的机会，把它改成每轮阻塞一个 tick 后，低优先级任务才真正能稳定执行。

蜂鸣器的声音有点太大，感觉可以改外设代码调整，但为了避免引入更多变数，我就简单用电工胶布贴了一下减小音量。

到这里，Bad Apple 已经具备视频、音频、节拍 LED、交通灯和按键交互，足以作为一个比较完整的多任务演示了。我心满意足地离开了实验室，回看着刚刚录制的视频，忍不住轻哼了起来。

晚上继续推进原定的 GDB stub，不过我复用了前面的流程，调用 Windows 的 xPack 的 RISC-V 工具链中的 GDB，通过串口连接，试了一下断点停住（这个断点只能在源代码里设定，我没有实现硬件断点）、读取全部寄存器、查看 `0x80000000` 的 SDRAM 内容以及 continue 等，大致是可以使用了。

总体这两个应用还是很能体现 trap 在我们这个小型 SoC 系统上的应用的，我还是比较满意的，挺贴近真实的应用，而且我对这种“底层自己实现一个协议，接入已有的成熟开源项目”的工作还是很喜欢的。

现在感觉代码差不多写完了，不过现在 Makefile 目标又开始零散了起来（之前每个程序都有自己的 target），固件的文件夹也乱起来了，把测试样例、自己实现的 runtime、真正的用户程序混合起来了，因此我进行了一些整合，把 bootload 和编译链接脚本也整理了一下，便于后续的开发和演示。GDB 也不再只调试固定的 hello，而是可以给普通用户程序套上 GDB bootstrap，再复用现有 Bootloader 上传。

不过收尾时又发现 FreeRTOS 的专项测试仍然有一些环境和布局敏感问题。最开始怀疑是 task stack 太小或 deferred yield 的实现有竞争，临时做了加栈、调整切换时机等实验，但它们只会让失败位置发生变化，没有形成可信的修复，因此没有把试验代码塞回主分支。

## Day 8

今天尝试写硬件加速和自定义 ISA。最初考虑过 MMIO accelerator、RV32M、浮点、完整 SIMD，但完整浮点或 Vector 改动太大，普通 MMIO 又不够有辨识度。最后选择利用 DarkRISCV 已有的 custom-0 协处理器接口，实现一条 packed signed INT8 DOT4 指令 `dot4.s8 rd, rs1, rs2`。这个只能叫 SIMD 风味指令吧，显然不叫完整的 SIMD 扩展，后者确实不是很好做，也没什么板上资源和开发时间了。

实现过程并不是单纯写四个乘法器，还要处理连续两条 DOT4 请求，防止旧 ACK 被下一条指令错误复用；还要验证 stall、rd=x0、非法 custom 编码、timer IRQ 与协处理器指令边界。ISE 尝试上板，map 和 slack 都没有问题，但是 slice 达到了 92%，可能已经没法再新的东西了，那就在这里收尾吧。

然后还让组员去做新的实验，上板验证加速结果，也是非常喜人，和仿真一样达到了约 27x 的加速。同时还进行了其他的性能测试，总结结果准备编写报告。

最后重新规划了答辩的展示计划，大概分为三条主线，简单演练了一下。
