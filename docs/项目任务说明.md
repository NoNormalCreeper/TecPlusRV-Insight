# 项目任务说明：NexysRV-Insight

PPT 中题目 B 的要求是：基于 FPGA 开发板完成处理器设计；基础层次要求实现支持基本指令集的单周期或多周期 CPU，支持算术、逻辑、访存、跳转等指令并能运行测试程序；进阶层次要求集成内存与 I/O，构建完整可运行系统，分析性能瓶颈并量化时钟频率、CPI 与吞吐量；拓展层次要求在流水线、Cache、乘除法/浮点、自定义 ISA、AI/矩阵加速、PPA 权衡等方向中至少深入实现一项。

## 1. 项目名称

**NexysRV：基于 PicoRV32 的可验证、可观测、可扩展 RISC-V SoC 与 TinyAI 加速实验平台**

## 2. 项目定位

本项目选择课程设计题目 B：**基于 FPGA 开发板的处理器设计**。项目平台为 **Nexys 4 DDR**，处理器体系结构选择 **RISC-V RV32I/RV32IM 子集**，处理器核心以开源轻量级 RISC-V 处理器 **PicoRV32** 为基础，围绕该核心完成 FPGA 上的 SoC 系统集成、裸机软件栈、自动化验证、外设接口、性能剖析与自定义加速扩展。

项目目标不是简单地“让一个开源 CPU 在板子上跑起来”，而是完成一个具有工程闭环的软硬件系统：

```text
开源 RISC-V CPU 核
+ 自研 SoC 总线与地址译码
+ 片上 BRAM 存储系统
+ Memory-mapped I/O 外设
+ UART 控制台
+ 裸机 C SDK
+ 自动化仿真与板级验证
+ 性能计数器与 PPA 分析
+ TinyAI / 自定义指令加速扩展
```

本项目符合题目 B 对“鼓励参考开源实现与 AI 工具完成核心模块，但须独立完成需求与接口定义、工程审阅、硬件平台落地调试、系统集成与联调验收，并能讲清系统设计原理”的要求。

# 3. 总体目标

本项目分为三个层次完成。

## 3.1 基础层次：基于 FPGA 的 RISC-V CPU 运行闭环

基础目标是完成一个可综合、可仿真、可上板运行的 RISC-V 处理器系统。

具体包括：

```text
1. 在 Nexys 4 DDR 上完成 PicoRV32 处理器核心集成。
2. 配置并解释 PicoRV32 的 RV32I/RV32IM 指令支持范围。
3. 建立 CPU 与 BRAM 存储器之间的指令/数据访问通路。
4. 支持算术、逻辑、访存、跳转、分支等基本指令类型。
5. 编写裸机测试程序，验证 CPU 能够正确执行基础指令序列。
6. 完成 Vivado 工程建立、综合、布局布线、bitstream 生成与硬件下载。
7. 在 Nexys 4 DDR 板上通过 LED、数码管或 UART 显示运行状态。
```

基础层次的最低验收现象：

```text
FPGA 下载 bitstream 后，CPU 从片上 BRAM 中取指运行；
测试程序完成后，通过 LED/数码管/UART 输出 PASS 状态；
若测试失败，输出对应错误码。
```

基础测试程序至少包括：

```text
1. ALU 测试：add/sub/and/or/xor/slt 等。
2. 立即数测试：addi/andi/ori/xori/lui/auipc 等。
3. 访存测试：lw/sw/lb/lbu/sb 等。
4. 分支跳转测试：beq/bne/blt/bge/jal/jalr 等。
5. 循环程序测试：累加、Fibonacci、GCD 或数组求和。
```

## 3.2 进阶层次：完整 SoC 系统设计

进阶目标是在 CPU 基础上集成内存子系统和基本 I/O 接口，构建一个可运行裸机 C 程序的小型计算机系统。PPT 明确要求进阶层次完成 CPU、内存子系统与基本 I/O 接口的系统集成，并能够支持小型测试程序完整运行、分析系统性能瓶颈和提出优化方案。

本项目的 SoC 结构如下：

```text
                 ┌────────────────────┐
                 │     PicoRV32 CPU   │
                 │   RV32I / RV32IM   │
                 └─────────┬──────────┘
                           │ native memory bus
                           ▼
                 ┌────────────────────┐
                 │  TinyBus / Decoder │
                 └──────┬──────┬──────┘
                        │      │
          ┌─────────────▼┐   ┌─▼────────────────────────┐
          │ BRAM Memory  │   │ Memory-mapped I/O        │
          │ 程序/数据/栈   │   │ GPIO/UART/Timer/Perf/Debug│
          └──────────────┘   └──────────────────────────┘
                                      │
                                      ▼
                            Optional Accelerators
                            DOT4 / POPCOUNT / CRC
```

### 3.2.1 存储系统

主线采用片上 BRAM 作为程序和数据存储。Nexys 4 DDR 板上虽然有外部 DDR2，但 DDR2 接入需要 memory controller / MIG，风险较高，因此本项目将 DDR2 作为拓展研究项，而不是基础依赖。

基础存储规划：

```text
0x0000_0000 - 0x0001_FFFF    BRAM，放置 .text/.rodata/.data/.bss/stack
0x1000_0000 - 0x1000_00FF    MMIO 外设区域
0x2000_0000 - 0x2000_0FFF    加速器/调试寄存器区域
```

报告中需要说明：

```text
1. 为什么基础系统使用 BRAM 而不是 DDR2。
2. BRAM 容量如何划分给程序、数据、栈。
3. 若后续扩展 DDR2，地址空间如何映射。
4. Cache 设计暂不作为主线，但给出存储层次规划：
   BRAM 作为片上低延迟存储；
   DDR2 可作为后续大容量主存；
   Cache 可作为 CPU 与 DDR2 之间的延迟隐藏层。
```

这可以满足 PPT 中“含 Cache 设计或存储层次规划”的要求。

### 3.2.2 Memory-mapped I/O

设计统一 MMIO 地址空间，使裸机 C 程序可以通过普通 load/store 指令访问外设。

建议地址映射如下：

```text
0x1000_0000    LED 输出寄存器
0x1000_0004    拨码开关输入寄存器
0x1000_0008    按键输入寄存器
0x1000_000C    七段数码管输出寄存器
0x1000_0010    UART 数据寄存器
0x1000_0014    UART 状态寄存器
0x1000_0020    cycle counter
0x1000_0024    instret counter
0x1000_0028    benchmark 控制寄存器
0x1000_0030    test exit / pass-fail 寄存器
0x1000_0040    trace/debug 控制寄存器
```

示例 C 代码：

```c
#define MMIO32(addr) (*(volatile unsigned int *)(addr))

#define LED       MMIO32(0x10000000)
#define SWITCH    MMIO32(0x10000004)
#define UART_DATA MMIO32(0x10000010)
#define CYCLE     MMIO32(0x10000020)
#define TEST_EXIT MMIO32(0x10000030)

int main(void) {
    LED = SWITCH;
    TEST_EXIT = 1;
    while (1) {}
}
```

### 3.2.3 裸机 C 软件栈

建立最小 RISC-V 裸机软件开发环境，使系统不仅能运行手写机器码，也能运行 C 程序。

需要实现：

```text
1. linker.ld：定义 ROM/RAM/MMIO 地址布局。
2. startup.S：设置栈指针，清零 .bss，初始化 .data，跳转 main。
3. mmio.h：定义外设寄存器地址。
4. gpio.c：LED、开关、按键访问接口。
5. uart.c：串口输出接口。
6. timer/perf.c：cycle、instret、benchmark 计数接口。
7. print-lite：轻量级 puts、print_hex、print_dec。
```

不要求移植完整 libc，不依赖操作系统，不使用复杂 malloc。若需要动态内存，可实现一个简单 bump allocator 作为拓展。

## 4.1 亮点一：Verification-first 自动化验证体系

本项目采用“先仿真、再上板”的验证策略。所有关键功能先在仿真环境中通过，再进入 Vivado 综合和 Nexys4 板级调试。

验证流程：

```text
firmware.c / startup.S / linker.ld
        │
        ▼
riscv64-unknown-elf-gcc
        │
        ▼
firmware.elf
        │
        ├── objdump 反汇编检查
        ├── objcopy 生成二进制
        └── bin2mem 生成 BRAM 初始化文件
        │
        ▼
Verilator / Icarus / Vivado 仿真
        │
        ├── UART log
        ├── MMIO pass/fail
        ├── VCD 波形
        └── 自动退出码
        │
        ▼
Vivado 综合、实现、上板验证
```

仿真机制：

```text
1. testbench 监听 0x1000_0030 test exit 寄存器。
2. firmware 写入 0x00000001 表示 PASS。
3. firmware 写入 0xdeadxxxx 表示具体失败类型。
4. testbench 自动输出测试结果并结束仿真。
```

测试类型：

```text
1. ISA smoke test
2. BRAM memory test
3. MMIO GPIO test
4. UART test
5. benchmark test
6. accelerator correctness test
```

该亮点体现“系统验证的完整工程闭环”，与 PPT 对功能仿真、硬件调试和系统测试的统一要求一致。

## 4.2 亮点二：统一 TinyBus 外设接口

设计一个统一的片内轻量级总线接口，避免所有外设直接写在一个巨大的 `soc.v` 里。

统一接口形式：

```verilog
module tinybus_slave (
    input         clk,
    input         resetn,

    input         valid,
    input  [31:0] addr,
    input  [31:0] wdata,
    input  [3:0]  wstrb,
    output [31:0] rdata,
    output        ready
);
```

所有外设均按统一 slave 风格实现：

```text
gpio_slave
uart_slave
timer_slave
perf_slave
debug_slave
accel_slave
```

地址译码器负责：

```text
1. 根据地址选择唯一 slave。
2. 转发读写请求。
3. 汇总 ready/rdata。
4. 避免多个外设同时响应。
5. 对非法地址返回错误码或默认值。
```

该亮点体现工程抽象能力：系统不是把 CPU、LED、UART 硬拼在一起，而是形成一个可扩展的 SoC 结构。

对于快外设，例如 LED：

```
CPU 写一次 MMIO
→ 立即 ready
→ LED 寄存器更新
```

对于慢外设，例如 I2C/SPI：

```
CPU 写 CTRL.START
→ 立即 ready
→ 控制器后台工作
→ CPU 轮询 STATUS.DONE
→ CPU 读 DATA
```

不要让 CPU 的一次 load/store 卡住几千个周期等 I2C 传输完成。那样虽然能做，但系统体验和调试都会很差。

对于流式外设，例如 UART/Ethernet：

```
CPU 写 TX_DATA
→ 数据进入 FIFO
→ UART/Ethernet 控制器慢慢发
→ CPU 读 STATUS 判断 FIFO 是否满/空
```

所以可能需要补充几个通用组件：

```
1. tinybus_decode.v：地址译码
2. gpio_slave.v：LED/SW/Button
3. sevenseg_slave.v：数码管寄存器 + 扫描控制
4. uart_slave.v：UART TX/RX + status
5. spi_master_slave.v：SPI 控制器，用于 ADXL362
6. i2c_master_slave.v：I2C 控制器，用于 ADT7420
7. perf_counter_slave.v：cycle/instret
8. debug_trace_slave.v：trace/debug
9. eth_tx_slave.v：可选，以太网发包
```

## 4.4 亮点四：性能计数器与 CPI/吞吐量分析

实现硬件性能计数器：

```text
cycle counter：系统运行周期数
instret counter：已提交指令数
mem_wait counter：访存等待周期数，可选
io_access counter：I/O 访问次数，可选
accel_active counter：加速器工作周期数，可选
```

软件通过 MMIO 读取计数器，用于计算：

```text
CPI = cycle / instret
throughput = workload_size / cycle
speedup = cycles_baseline / cycles_optimized
```

需要比较至少三种配置：

```text
配置 A：基础 PicoRV32 SoC
配置 B：PicoRV32 + M 扩展 / fast mul
配置 C：PicoRV32 + 自定义 TinyAI / DOT4 / POPCOUNT 扩展
```

最终报告中给出：

```text
1. benchmark cycles
2. instruction retired
3. CPI
4. speedup
5. LUT/FF/BRAM/DSP 资源占用
6. Fmax / timing slack
7. 功能、性能、面积之间的权衡
```

该部分直接对应 PPT 中“对时钟频率、CPI、吞吐量进行量化评估”和“PPA 三角约束下给出设计权衡说明”的要求。

## 4.5 亮点五：TinyAI INT8 自定义加速扩展

本项目的核心技术亮点不是简单做乘法器，而是面向 AI/矩阵计算设计一个轻量级 INT8 加速扩展。

### 方案 A：DOT4 自定义指令 / 协处理器

设计一个 `DOT4` 加速单元：

```text
rs1 = [a0, a1, a2, a3]    四个 int8
rs2 = [b0, b1, b2, b3]    四个 int8

rd = a0*b0 + a1*b1 + a2*b2 + a3*b3
```

应用场景：

```text
1. INT8 向量点积
2. 小型量化线性层
3. TinyAI 分类 demo
4. 矩阵乘法内核的一小步
```

软件对比：

```text
版本 1：纯 RV32I 软件实现 int8 dot product
版本 2：使用 RV32IM 乘法实现
版本 3：使用 DOT4 加速扩展实现
```

衡量指标：

```text
1. 计算结果正确性
2. cycle 数
3. instret 数
4. CPI
5. speedup
6. LUT/FF/DSP 增量
7. Fmax 变化
```

### 方案 B：POPCOUNT / Hamming 扩展

补充实现一个 `POPCOUNT` 或 Hamming distance 加速器：

```text
popcount(x)：统计 32-bit 数据中 1 的个数
hamming(a, b)：popcount(a ^ b)
```

应用场景：

```text
1. 二值向量相似度
2. 简单检索任务
3. 数据压缩/校验辅助
4. AI 中的 binary neural network / bitset 计算类比
```

这个扩展硬件复杂度低，但工程意义清晰，适合与 DOT4 共同构成“面向 AI/数据处理的自定义扩展指令集”。

## 4.6 亮点六：Trace Buffer / Debug Monitor

为解决 FPGA 上调试困难的问题，设计一个轻量级可观测模块。

最低版本：

```text
1. 记录当前 PC。
2. 记录最近一次访存地址。
3. 记录最近一次写数据。
4. 记录 trap 状态。
5. 通过 MMIO 或 UART 输出。
```

进阶版本：

```text
用一小块 BRAM 实现 trace buffer，记录最近 N 条事件：

cycle
pc
mem_addr
mem_wdata
mem_wstrb
mem_ready
trap
```

当测试失败时，firmware 或 debug 模块通过 UART dump 最近执行轨迹，用于定位问题。

该亮点的价值是体现“可调试系统设计”，而不是只依赖 LED 和肉眼观察。

## 4.7 亮点七：UART Bootloader，区分硬件配置与软件加载

普通 FPGA 课设中，每换一个程序都需要重新生成 bitstream。本项目可选实现 UART bootloader，使硬件配置和用户程序加载解耦。

普通流程：

```text
修改 C 程序
→ 重新生成 firmware.mem
→ 重新综合/实现
→ 重新生成 bitstream
→ 重新下载 FPGA
```

Bootloader 流程：

```text
固定 bitstream
→ PC 端 Python 脚本通过 UART 发送程序
→ 板上 loader 写入 BRAM
→ 释放 CPU reset
→ CPU 从 BRAM 运行新程序
```

这不是必做项，但如果完成，会成为非常强的工程亮点。

## 4.8 亮点八：小范围 Assertion / 形式化检查

不要求验证整个 PicoRV32 核，但可以对自研模块加入 SystemVerilog assertion 或 testbench 检查。

建议检查：

```text
1. 地址译码唯一性：同一请求最多只有一个 slave 响应。
2. 只读寄存器不可被写改变。
3. valid 请求最终产生 ready。
4. MMIO 写使能与 wstrb 行为一致。
5. 加速器 busy 期间不会错误响应新请求。
6. test exit 只能由 firmware 明确写入。
```

这部分可以作为报告中的“工程可靠性设计”章节，不必过度展开。

# 11. 学术诚信与开源使用边界

```text

6. AI 生成内容是否经过人工审阅、仿真验证和上板验证。
```

题目 B 允许并鼓励参考开源实现与 AI 工具，但要求独立完成需求与接口定义、工程审阅、硬件落地调试、系统集成与联调验收；如果不做审阅整合、无法独立讲清系统设计原理，直接照搬仍视为学术不端。

# 12. 最终一句话版本

这个项目最终可以这样概括：

**我们基于 Nexys 4 DDR 和 PicoRV32 构建了一个可运行、可验证、可观测、可扩展的 RISC-V SoC。系统支持裸机 C 程序运行，具备 BRAM 存储、MMIO 外设、UART 控制台、性能计数器和自动化仿真验证；在此基础上实现面向 TinyAI/数据处理的 DOT4 与 POPCOUNT 自定义扩展，并通过 cycle、CPI、speedup、资源占用和时序报告完成 PPA 权衡分析。**
